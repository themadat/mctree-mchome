# Shared components

## Hosted access gate

Every normal browser load shows only the McFamily introduction, hosted status, and one passphrase field until the latest public ciphertext vault is fetched. The passphrase stays in the browser, is tested locally against every grant until exactly one match is found, unwraps only the data key assigned to that grant, and must decrypt a strict dataset 16 package before the workspace opens. Account labels and roles are not listed before sign-in. A missing vault exposes one clearly labelled Owner recovery ZIP path; after a validated Editor recovery import, that browser enters Owner Setup and can publish the first encrypted vault. Older packages, loose CSVs, blank families, demos, JSON/GEDCOM, and passphrase bypasses are unsupported.

## Family workspace

Desktop coordinates a header-toggled directory, SVG Family Tree, and profile columns; global Audit, Add, and PDF actions live only in the application title bar. The directory and selected-person columns can be closed independently so the Family Tree can fill the workspace, and pointer/keyboard dividers resize its horizontal splits. Developer Mode shows a divider percentage only during an active pointer drag. Directory search and its result-count pill share one bordered control in the module title bar, so the full `Search Directory…` placeholder stays readable at the default width; the pill shows the total alone until a filter or search narrows the list. Visible Filter By and Sort By controls are the same size and provide a checkbox menu for combinable living-status and Lineal/Non-Lineal filters plus first/last-name sorting; Sort By draws its own chevron instead of native select chrome. Lifespan and lineage context remain in each row, and the A–Z quick-jump rail follows the filtered results. Mobile uses touch-sized Directory, Family Tree, and Person tabs; selecting a person from the directory opens Person. All modes share the same selected-person state.

The Family Tree toolbar puts Full Tree to the left of Lineage and Details to the left of the default Summary view. Each mode uses an icon over its visible label, and every grouped heading is centered over its controls. Full Tree clears and closes the selected-person profile; Lineage stays disabled until a person is selected. Preferred/Legal/Lineal and Short/Full fill equal-height internal toggle groups without overflowing their Name Preferences container. Directional symbols sit to the left of the native Ancestors and Descendants number controls, which accept 0 through 10. The toolbar also includes an off-by-default ?? Lineal button in Full Tree, a right-aligned editable zoom value with an adjacent `%` and stacked far-right one-percent buttons, icon-over-label Out, In, and Fit actions, and an off-by-default Non-Lineal Lines overlay. Both display toggles keep fixed symbols in either state, and enabling ?? Lineal centers the revealed unresolved-Lineal people at natural scale. Depths default to 10, and every toolbar group or toggle shares one control height. Recorded Non-Lineal parent links are hidden while the overlay is off and drawn as light dashed branches while it is on; faded muted-red parent edges trace the Lineal bloodline, and Lineal adoption uses the same muted red with a dashed stroke. Its canvas scrolls horizontally and vertically whenever the natural-size layout exceeds the viewport; ordinary wheel input scrolls and Ctrl/Command-wheel zooms. Cards are narrow and stack every whitespace-separated name part on a new line, expanding the generation row vertically when needed. Lineal cards preserve the standard living or deceased fill and use a bold muted-red outline plus a small lineage symbol beside the lifespan, while selection replaces either lineage or ordinary borders with the same accent stroke. Neither tree mode uses a portrait or initial placeholder, and internal person references appear only in Developer Mode. Up to two previous partners stay to the left in oldest-to-newest order at two-thirds scale, while the current or latest death-ended spouse remains full-size on the right. One left partner is vertically centered; two align to the full-size cards' top and bottom. Their straight gold lines remain parallel and evenly spaced. Current marriages are solid, previous marriages are dashed, never-married partnerships are dotted, and unknown relationships use repeated question marks. A collapsible Key floats at the upper right of the canvas and lists those four partner states before Lineal parent, Lineal adoption, and Non-Lineal parent lines. Person nodes are native SVG buttons by role and expose accessible labels; relationship paths also have textual descriptions.

Favorite P references, hint dismissals, individual What’s New dismissals, and Directory visibility are stored as small device-only preferences. They survive hosted record replacement and Lock. Reset Preferences clears dismissals and Directory visibility while retaining favorites; Erase Everything removes them all.

## Person and relationship editors

The selected-person header places icon-over-label Delete and Edit actions immediately before the X close control. Add and Connect use the same convention in the Relationships heading. There is no selected-person Set as home action. Identity properties are ordered Born, Died, Age, Living Status, and Marital Status; Gender and Pronouns remain stored but hidden. A living person's Died value is `----`. Age uses natural years/months wording on one line; a deceased age adds italic `Would be`, a bold-italic current age, and italic `today`. The person dialog uses structured name and life fields plus repeatable address, phone, and email groups. Add Relative creates a person and a relationship in one flow. Connect Relative links existing people. Parent editing chooses Lineal/Non-Lineal separately from Biological/Adopted/Step/Foster/Guardian/Unknown. Relationship metadata lives only on relationship records.

Destructive controls use the shared confirmation dialog. Deleting a person creates recovery and removes all attached relationships. Validation errors are shown without closing the editor or changing stored data.

## Dialogs and focus

`components.openDialog()` records its trigger, opens a native modal, and moves focus to the requested or first appropriate control. Closing restores focus. Confirmation, message, import-preview, person, relationship, Notes, and Settings dialogs use this lifecycle. On small screens application dialogs become full-screen surfaces with a single scrolling panel.

## Toasts and status

`components.toast()` reports saves, exports, imports, recovery, and update availability through reusable status UI. The floating status shows local save and backup state only. Completion and errors are also announced in polite or assertive live regions as appropriate.

## Access and audit

Audit appears immediately left of Add and only for Owner and Editor, using the shared terminal-on-rectangle symbol. Notes follows Add, then PDF uses the filled document symbol. The Audit modal's top row contains exactly three compact same-line summaries: signed-in username plus permission role, encrypted family file status, and a green/red GitHub connection control that expands its details directly below the row. The Owner's permission appears as Admin. Admin and Editor see Update, Lock, and newest-first audit history; Owner Recovery and access grants remain Admin-only. Summary of What Changed is manual, while Detailed Changes is generated from the hosted baseline and excludes personal device preferences. No Updates disables the symbol-labelled Update control. Admin publications record `Admin`; named Editors record their signed-in username. Owner alone sees the required Owner grant plus dynamic lists of up to 20 separately named Editors, 20 Members, and 20 Viewers. Every recipient can be added or revoked independently; generated phrases use three words and custom phrases require eight characters. Member and Viewer receive no Audit button, shortcut, or modal and never receive person/family Notes, routine import, download, PDF, Developer-data, publication, token, or passphrase-management controls.

While the Owner has Developer Mode enabled, the role pill opens a keyboard-accessible quick-change menu for Owner, Editor, Member, and Viewer previews. The transient preview drives the same editing, PII, Notes, PDF, Audit, imported-source, and developer-tool gates as that role without changing the signed-in grant, vault, package, or credentials. Leaving Developer Mode or reloading restores Owner behavior.

Add/Edit Person uses a compact two-column desktop editor that fits at 1280 × 720 with one address row. Birth (Lineal), Current (Legal), and Preferred (Display) each keep Prefix, First, Middle, Last, and Suffix on one `5/30/30/30/5` weighted row; Maiden aligns its Last field with those rows, and every name subheading sits inside rather than interrupting its card border. For a new person, each Birth field mirrors into Current and Preferred until its target is manually edited. Details puts Birth and Death dates before the same-height Living status. Date descriptors derive automatically from blank, exact, or question-mark partial values; invalid shapes and impossible known dates show comprehensive red examples and disable Save. At least one First name is required, valid death input selects Deceased, and email/address validity participates in the same Save gate. Gender, Pronouns, birth/death place, and lineage background are omitted while existing values remain preserved. Editor Notes contains one textarea. Address, phone, and email remain separate full-width lines, and one address uses a compact single-row desktop editor. Save and Cancel use the shared checkmark-seal and X-mark-seal symbols. Add Person has searchable Parents, Partners, and Children pickers. Selecting a Partner reveals status plus start and end dates; saving translates that status into the authoritative partner type and end reason fields. The complete relationship set is validated before either the person or links are stored. The relationship form previews the resulting Lineage ID when Parent lineage is Lineal, then assigns it atomically with the relationship and rebases existing Lineal descendants when needed.

Publication is explicit. The full and physically redacted packages are validated and encrypted in memory before GitHub receives one ciphertext-only `data/mcfamily/McFamily-access.json` vault containing both encrypted packages and their access grants. No second encrypted-directory file is used. Busy, success, setup, validation, wrong-passphrase, stale-copy, and network failures use labelled status text and live regions. Member and Viewer sign-ins do not write audit events because they have no GitHub write credential.

## Notes

Family Notes remains one large plain-text textarea for Owner and Editor access. It opens from the header or `N`, autosaves locally, and returns focus when closed. Person-profile Notes are also limited to those roles. Member and Viewer modes omit the person section, header action, shortcut, search result, Help topic, and dialog content. The current `documents` collection is normalized to one `app-notes` document.

## Global search

`/` focuses the larger global search outside editable controls. The search field is centered in the desktop title bar and the results dropdown exactly matches its width. Directory sits to its left and Favorites to its right; both follow the header icon-over-label convention, Directory toggles its pane in either direction, and Favorites toggles every starred person directly below Search. Owner/Editor Developer Mode shows a List Star Restore control immediately after Favorites and opens the same private JSON picker as Developer Settings. Directory and global search support partial substrings and in-order fuzzy characters. Owner/Editor results include people, contact data, life places, heritage, notes, the Notes document, Help topics, releases, and Roadmap items; Member and Viewer searches exclude Notes, while Imported Source participates only in Owner/Editor Developer Mode and always excludes `Source Last Modified By`. Person rows lead with the display name and add Birth and Current names inside one parenthetical only when they differ from the display name and each other. A separate star toggle remains beside each person. Starred rows and controls use a strong gold highlight, persist through hosted replacement and Lock in device preferences, sort before other matching people, and appear together while Favorites is expanded. Developer Mode can also download a private Favorites JSON file and restore its P references after browser storage is cleared. A person result selects that person, returns the Family Tree to Lineage mode, and routes to Profile on mobile.

## Lineage

Lineage appears directly under identity details and above Relationships. Identity details show partial source dates with `??` and `????` placeholders when the strict normalized value cannot hold them. Age uses natural wording such as `34 years old`, `15 months old`, or `75 years old at death · Would be 176 today`, and prefixes approximate values with `~`. Living Status and a perspective-aware Marital Status follow Age. When a current marriage has no recorded ending, two deceased partners remain Married; when only one is living, the living person's status reads Widowed. Partners rows read `(year :: Status)` from the same perspective.

The selected-person profile places Names before Lineage. Its property labels use a 126px column, and name labels remain on one line, including `Preferred (Display)`. Birth, Current, and Preferred name cards each show Prefix, First, Middle, Last, and Suffix with explicit `UNKNOWN` values; Maiden Last Name is a separate property. The profile heading follows Preferred → Current → Birth. Lineage then presents the complete two-digit source Lineage ID from oldest ancestor to selected person. The first three segments are italic and the final segment is bold, so a one-, two-, or three-part ID ends with bold italic text. A Family Line heading introduces paired name and relationship-reading cells built from direct lineage-parent references; each left cell uses `Name [## | G#]`. Each pair shares one row height and centers its content vertically so wrapped names remain aligned with its reading. Ancestor, sibling, and descendant totals span both columns beneath the rows. Every resolved person remains linked to their profile and tree focus. Readings include the generation and the parent's first whitespace-separated name, such as `Gen 6, 5th Child of Max`; unknown positions omit only the ordinal, and the root reads `Gen 0, Root ancestor`. The printable atlas includes the same ID, Family Line, reading, and totals without interactive controls.

Relationships use compact, initially open Parents, Siblings, Partners, and Children groups in that order. Parents, siblings, and children show their generation. Parent names identify both role and type, such as `Lineal :: Adopted` or `Non-Lineal :: Biological`; siblings and children show two-digit birth order plus birth year, and partners show start–end years with their perspective-aware status. The one recorded Lineal parent appears first, followed by every Non-Lineal parent, while the current partner appears first in bold before reverse-chronological, de-emphasized previous partners. Owner/Editor gets an Edit control beside every partner history. Its form records partner relationship type independently from end reason, so ongoing, death, divorce, separation, annulment, and unknown endings retain their exact McRelations meaning with dates, place, and notes. Screen and print profiles preserve the same order and context. Person Notes appear after Relationships only for Owner/Editor. Imported Source appears last only for Owner or Editor access while Developer Mode is enabled.

Family Tree generation rows compare the numeric lineage segments directly in root-to-person order rather than falling back to display names. Name controls independently switch between Lineal (Birth) and Legal sources and between Short (First, Last, Suffix) and Full (all five parts); the defaults are Lineal and Short. Partner arrangement places every relationship with a recorded ending on the Lineal person's left in chronological order and exactly one unended current partner on the right. McRelations rows retain partner type and end reason as the authoritative history; a blank ending can be interpreted against both people's living status without rewriting the imported record, and stable relationship order remains a deterministic fallback.

The profile X closes the panel and clears the selected-person state. Full Tree also closes and deselects the profile, and Lineage remains disabled until selecting a person. Selecting a tree node reopens the profile. There is no separate Show person control.

Family-record mutation controls require both `features.familyEditing` and active Owner or Editor hosted access. Member and Viewer do not render Add in the title bar or Add, Connect, Edit, Delete, and empty-profile Add Person in Selected Person; family-title and Notes changes remain unavailable. Their routine ZIP import/export, PDF, Developer data, and publication surfaces are also absent. Home-person assignment remains internal. Personal view settings and Favorites stay available in every mode.

## Print report

The print host remains hidden and inaccessible during normal operation. Print / Save PDF builds it from normalized state and normally invokes the native dialog; in Developer Mode it instead copies the report into a closable in-app preview. Compact opening content flows into six-column family maps. George McMillen (1745) is the first root at Generation 0, and Generation 4 and later are grouped beneath Generation 3 family lines. Every component is labelled by its root ancestor, while unresolved `99`/`??` lineage branches are omitted. Each generation begins on its own row and contains name-and-years cards without IDs. Lineal cards have clearly visible faded-red outlines; Newton, Albon, and Lucian receive the stronger orientation highlight and a Bloodline symbol, while adaptive name type keeps names to two lines. A dense Person Directory follows without P references, individual Notes, or Imported Source fields.

## Icon conventions

Use the shared inline SVG catalog in `assets/js/icons.js` for standard controls. Controls still need visible text or an accessible name; state is never communicated by icon or color alone.

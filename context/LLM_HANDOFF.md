# Agent handoff

Start a new session with:

```text
Continue work in /Users/stripes/Documents/GitHub/mctree-mchome. Read AGENTS.md and context/LLM_HANDOFF.md first. Preserve manual edits and run git status --short before editing.
```

This repository is McFamily, a static family atlas. Version `0.0.1.93` uses a latest-only schema v13 browser namespace and strict dataset 17.0.x packages internally. Normal recipients use one public Pages link: `core/cloud.js` anonymously fetches a ciphertext-only JSON vault from the public `themadat/mcdata` repository, then tests the entered passphrase locally against every grant and requires exactly one match before PBKDF2 plus AES-GCM opens its Owner, named Editor, named Member, or named Viewer package. No account label or role is listed before sign-in. Owner and separately named Editors decrypt the full record and may publish; the Owner's permission and publication actor display as Admin, while Editors publish under their matched username. Owner alone adds, rotates, or removes up to 20 grants for each non-Owner role, and every active grant must have a unique passphrase. Members decrypt full PII read-only but have no person or family Notes interface. Viewers receive only a separately encrypted package where places, residences, contacts, family Notes, and unstructured record notes were removed before encryption. Read-only modes omit routine recovery ZIP, import, PDF, developer-data, and publishing controls. Imported Source appears and participates in search only for Owner/Editor in Developer Mode. The passphrase gate reappears on every reload and the encrypted vault is never service-worker cached. There is no custom backend, account provider, cloud database, or runtime dependency.

The main product invariants are now the hosted passphrase gate, strict decrypted-package validation, directory/tree/profile workspace, single Notes modal, Settings/Roadmap, Owner recovery, encrypted GitHub publication, themes, accessibility, and install shell. Do not restore the removed Records interface, multi-note workspace, rich-text editor, or plaintext automatic synchronization.

## Workflows

### `wish`

Record an idea in `context/WISHES.md` without planning or implementing it.

- Check for duplicates and use the next `WISH-###` id.
- Capture behavior, rationale, priority, effort, acceptance criteria, constraints, affected files, and material open questions.
- Set the status to `Proposed`.

### `plan`

Investigate a wish without implementing it.

- Create or revise `context/WISH-###-slug-PLAN.md`.
- Put a `## Resume` section first, followed by decisions, scope, non-goals, file map, accessibility/responsive considerations, tests, and open questions.
- Link it from the wish and set the status to `Planned`.
- Do not change runtime files, build ids, or cache ids.

### `start`

Implement an approved plan.

- Read the wish and plan, set the wish to `Active`, and keep Resume current.
- Add only the architecture the feature needs; keep the app static and dependency-free.
- Preserve the schema-v13 privacy, validation, latest-only storage, accessibility, and offline invariants below.
- Advance the four-part application version and verify affected workflows.

### `cut`

Finalize an active line as a release.

- Confirm the semantic version and reset build to `1` for a new major/minor/patch unless another value is requested.
- Update config identity, release notes, asset queries, manifests when needed, and service-worker ids.
- Mark the wish Shipped and record version/date.
- Run `docs/TESTING.md`.

Do not silently move between lifecycle stages.

## Data and privacy invariants

- Never commit a real family CSV, ZIP, spreadsheet, PDF, screenshot, name list, address, phone, email, heritage note, or family note. The entire local `data/` directory is ignored; use synthetic committed fixtures only.
- Normal first launch requires an online encrypted vault plus a valid hosted passphrase. Before revision 1 exists, an existing local Editor workspace may initialize Owner setup from one validated recovery ZIP. There is no loose-CSV, demo-family, blank-family, JSON/GEDCOM, or deployed bypass path. `?local=1` bypasses only on localhost for UI testing.
- The public data repository contains one generated JSON vault at `data/mcfamily/McFamily-access.json`: access grants plus the separately encrypted full and Viewer family packages, along with salts/nonces, PBKDF2 iterations, wrapped random keys, access labels/modes, dataset version, timestamp, and revision. It does not use a second encrypted-directory file. Passphrases, GitHub tokens, readable CSVs, and ZIPs must not enter it.
- Owner and each named Editor grant wrap both full and redacted data keys so an existing publisher can update both ciphertext payloads without knowing recipient passphrases. Dynamic recipient ids use `editor-…`, `pii-…`, or `redacted-…`; original fixed role ids remain accepted for version-1 vault compatibility. The stable internal `pii-viewer` and `redacted-viewer` values display as Member and Viewer respectively. All shown names and passphrases are unique. Names remain public vault metadata for access management and audit identity but are not shown by the locked screen; the matched Owner/Editor label is the immutable actor for a publication. Each Member wraps only the full key; each Viewer wraps only the redacted key. Removing a grant blocks future reloads but cannot erase previously viewed or copied information. Member and Viewer sign-ins are not centrally auditable without a backend or write credential.
- Maximum family size is 1,500 people.
- The strict five-file ZIP remains the internal validated plaintext representation and the Owner recovery artifact. It is not the ordinary recipient handoff. Imports replace; they do not merge. Hosted sessions keep the decrypted working state only in memory and use the encrypted GitHub vault plus commit history as the saved source; only local-only replacement and deletion create a browser recovery snapshot.
- Deleting the final person leaves an initialized empty workspace.
- Parent and partner links are explicit records. A parent row stores Lineal/Non-Lineal role separately from biological/adopted/step/foster/guardian/unknown type. Reject missing references, self-links, duplicates, a second Lineal parent for one child, and directed ancestry cycles; accept multiple distinct Non-Lineal parents without requiring them to be partners of the Lineal parent. Connecting a Lineal parent previews and assigns the child's root-to-person Lineage ID: preserve an already valid direct segment, otherwise retain an available prior final segment or use the next free `01`–`98` segment, and recursively rebase Lineal descendants. If an unnumbered Lineal parent has no Lineal parent of their own, first assign the next unused root segment.
- Derive ancestors, descendants, siblings, units, and lineage labels; do not cache them on people.
- Use only `mcfamily.state.v13` and local-only `mcfamily.recovery.v5`; do not load, unwrap, or migrate earlier browser state or recovery snapshots. Hosted sessions keep the full decrypted family only in memory and delete current or older full state/recovery keys plus the obsolete `mcfamily.cloud.baseline.v1`; GitHub is the saved source and Update is required before reload or Lock. `mcfamily.device-preferences.v1` contains only dismissed hint ids, dismissed release versions, Directory visibility, and favorite P references so those choices survive hosted replacement and Lock without retaining names, contacts, Notes, or other family content. `?local=1` on localhost remains full-state persistent for development and first-publication recovery setup remains local until the vault is created.

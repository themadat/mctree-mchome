Versioning rules for humans and agents
--------------------------------------

1. Determine the update type before changing the file. If an update contains more
   than one type, use the highest-impact type: major, then minor, then patch.

   Major — schema change
   - Increment major and reset minor and patch to zero.
   - Includes adding, removing, renaming, reordering, splitting, or combining columns.
   - Includes changing a column's meaning, data type, date representation, identifier
     format, relationship structure, delimiter, or character encoding.

   Minor — data update
   - Increment minor and reset patch to zero.
   - Includes adding or removing people or relationships, or recording new factual
     genealogy information without changing the schema.
   - Bulk factual updates count as one minor release when delivered together.

   Patch — correction
   - Increment patch only.
   - Includes correcting typos, whitespace, capitalization, misplaced values,
     duplicate records, malformed dates, or other errors in existing information.
   - A patch must not add a new column or change the meaning of a column.

2. Name every released CSV using this exact pattern:

   McLineage-<major>-<minor>-<patch>-<YYYY>-<MM>-<DD>.csv

   Example: McLineage-1-2-3-2026-08-19.csv

   - Use integers for major, minor, and patch.
   - Use a four-digit year and two-digit month and day.
   - The date is the date that version was last updated.

3. For every release:

   - Start from the latest validated version.
   - Choose the next version before editing and save the result under its new name.
   - Preserve stable P-formatted record_id values unless correcting an actual collision.
   - Store every person, including each partner, as a separate row with a stable P
     record ID. Store each partner relationship exactly once in the originating
     person's partner_relationships_json array, and leave source_row_number plus
     all lineage fields blank on partner-only rows.
   - Keep lineage_id as the complete oldest-to-newest path with two-digit segments,
     such as 01.01.01.03.02.02.04.02.01.01. Every non-root path must extend its
     direct parent's path by exactly one segment. Store the direct parent P reference
     in parent_consanguinity_person_id. When evidence identifies the partner who is
     also a parent, store that P reference in parent_affinal_person_id; otherwise
     leave it blank. The referenced parents must also form a recorded partner pair.
     Older direct parent_lineage_id and lineage_parent_id sources remain compatible.
   - Give each partner relationship a stable R-formatted relationship_id. Store its
     partner_person_id, relationship_type, relationship_order, start/end date value
     and descriptor fields, and end_reason. Blank end_reason means no ending is
     recorded; UNKNOWN preserves genuine ambiguity.
   - Store known date values as YYYY, YYYY-MM, or YYYY-MM-DD. Unknown digits may be
     represented by question marks anywhere in the same shapes and must use the
     partial descriptor. Do not use invalid as a descriptor.
   - Person date descriptors may be year, month, day, partial, UNKNOWN, or
     blank; birth descriptors cannot be blank, while a blank death descriptor means
     living.
   - Use UNKNOWN with a blank death value when the person is deceased but the date
     is unknown. Treat G0-G4 descendants without death values as deceased.
   - Record unresolved source problems in data_quality_notes instead of silently
     inventing or discarding genealogy facts.
   - Parse the complete CSV after editing and verify consistent column counts,
     unique record IDs, lineage/parent structure, and date value/precision pairs.
   - Update the Current dataset section and add a newest-first changelog entry.
   - Retain prior versions only in approved private storage. Never commit real family
     data, exported names, notes, or this private dataset to the source repository.

4. Use this changelog entry format:

   Version X.Y.Z — YYYY-MM-DD — [### KB (+#/-#/±0) | ### records (+#/-#/±0) | ## fields (+#/-#/±0)]
   Author: Person Name [Agent AGENT | Model MODEL | Effort EFFORT | Speed SPEED]
   Author: Person Name [Manual]
   Summary: One-line description of the release.

   - More detailed change.
   - Record-count or schema-count change, when applicable.
   - Validation performed and any remaining known limitations.

   The human author is required. Record assisted-agent details in the Author line;
   use [Manual] when no agent assisted.
   Ask the human author to supply unknown author or agent details before finalizing.
   Record the released CSV's decimal kilobyte size, rounded to the nearest whole KB,
   or "UNK" if the file is unavailable. In parentheses after each size, record count,
   and field count, record the change from the immediately preceding release using
   +#, -#, or ±0. Mark the initial release as "baseline"; use "UNK" when a prior
   value is unavailable.
   Copy model, effort, and speed from the active tool or interface when available.
   Never infer those settings; write "UNK" when they are unavailable.

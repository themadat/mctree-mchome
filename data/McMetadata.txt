Versioning rules for humans and agents
--------------------------------------

1. Determine the update type before changing the file. If an update contains more than one type, use the highest-impact type: major, then
   minor, then patch.

   Major — schema change
   - Increment major and reset minor and patch to zero.
   - Includes adding, removing, renaming, reordering, splitting, or combining columns.
   - Includes changing a column's meaning, data type, date representation, identifier format, relationship structure, delimiter, or
     character encoding.

   Minor — data update
   - Increment minor and reset patch to zero.
   - Includes adding or removing people or relationships, or recording new factual genealogy information without changing the schema.
   - Bulk factual updates count as one minor release when delivered together.

   Patch — correction
   - Increment patch only.
   - Includes correcting typos, whitespace, capitalization, misplaced values, duplicate records, malformed dates, or other errors in
     existing information.
   - A patch must not add a new column or change the meaning of a column.

2. Name every released package using this exact pattern:

   McFamily-<major>-<minor>-<patch>-<YYYY>-<MM>-<DD>.zip

   Example: McFamily-15-1-0-2026-08-25.zip

   - Use integers for major, minor, and patch.
   - Use a four-digit year and two-digit month and day.
   - The date is the date that version was last updated.

3. For every release:

   - Start from the latest validated version.
   - Choose the next version before editing and save the result under its new name.
   - Preserve stable P-formatted record-id values unless correcting an actual collision.
   - Keep exactly McPeople.csv, McPlaces.csv, McRelations.csv, McResidences.csv, and McMetadata.csv at the ZIP root. Do not add loose files,
     nested directories, or alternate filenames.
   - Store every person, including each partner, as a separate McPeople row with a stable P record ID. McPeople contains no parent or
     partner relationship columns.
   - Use kebab-case for every CSV header. Store Birth, Current/Legal, and Preferred/display names in their five structured name fields and
     store a changed birth surname separately in person-name-maiden-last. Display Preferred first, then Current/Legal, then Birth.
   - Prefix and suffix fields may be blank. Normalize known prefixes to Rev., Dr., Mr., Mrs., Ms., Miss, Fr., Father, Hon., Prof., Rabbi,
     Pastor, Capt., Col., Lt., Gen., Judge, or St.; normalize known suffixes to Jr., Sr., II, III, Esq., PhD, or MD. Do not infer an
     unrecognized prefix or suffix.
   - Birth and Current First/Last are required. Use UNKNOWN only when the source cannot supply a required value. Preferred/display and every
     other optional name part remain blank when they cannot be attributed confidently.
   - Keep lineage-id as the complete oldest-to-newest path with two-digit segments, such as 01.01.01.03.02.02.04.02.01.01. Every non-root
     path must extend its direct Lineal parent's path by exactly one segment.
   - Store every parent and partner exactly once in McRelations with a stable relationship-id and resolvable P references. Parent rows use
     lineal or non-lineal parent-kind. Partner rows store partner-type, relationship-order, dates, and end-reason. A Non-Lineal parent must
     be partnered with the child's Lineal parent.
   - Store reusable physical addresses in McPlaces with stable L IDs. Link people to places only through McResidences with stable RS IDs.
   - Store known date values as YYYY, YYYY-MM, or YYYY-MM-DD. Unknown digits may be represented by question marks anywhere in the same
     shapes and must use the partial descriptor. Do not use invalid as a descriptor.
   - Birth descriptors may be year, month, day, partial, or UNKNOWN and cannot be blank. A blank death value must use NONE for living,
     UNKNOWN for explicitly deceased, or UNKNOWN PRESUMED when source evidence presumes death.
   - Record unresolved source problems in data-quality-notes instead of silently inventing or discarding genealogy facts.
   - Update McMetadata package/dataset/schema rows, exact per-file counts, family data, and audit rows for every release.
   - Validate ZIP integrity, exact filenames and schemas, counts, unique IDs, date pairs, lineage structure, cross-file references,
     relationship rules, residence links, and ancestry cycles before accepting a release.
   - Update the Current dataset section and add a newest-first changelog entry.
   - Retain prior versions only in approved private storage. Never commit real family data, exported names, notes, or this private dataset
     to the source repository.

4. Use this changelog entry format for package releases:

   Version X.Y.Z — YYYY-MM-DD — [### KB (+#/-#/±0) | ### people | ### relations | ### places | ### residences | 5 files]
   Author: Person Name [Agent AGENT | Model MODEL | Effort EFFORT | Speed SPEED]
   Author: Person Name [Manual]
   Summary: One-line description of the release.

   - Records: # changed | # added | # deleted.
   - More detailed change.
   - Record-count or schema-count change, when applicable.

   The human author is required. Record assisted-agent details in the Author line; use [Manual] when no agent assisted. Ask the human author
   to supply unknown author or agent details before finalizing. Record the released ZIP's decimal kilobyte size, rounded to the nearest
   whole KB, or "UNK" if the file is unavailable. Record per-file counts so McMetadata and the changelog can be compared directly.
   Copy model, effort, and speed from the active tool or interface when available. Never infer those settings; write "UNK" when they are
   unavailable. Begin every changelog bullet list with changed, added, and deleted record counts when they apply. Keep routine validation
   results out of changelog bullets; record only material limitations or unresolved data concerns. Wrap prose and bullet text to a maximum
   of 140 characters per line, preserving indentation on continuation lines.
